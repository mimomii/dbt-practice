## ステップ1: stagingモデルを作る ✅完了

**目的**: ソーステーブルをそのまま軽くクリーニングする1:1モデルの書き方を覚える

## ステップ4: テストを書く ✅完了

**目的**: データ品質テストの書き方を覚える

**例**:
```yaml

  - name: stg_customer
```

**学べること**: ビルトインテスト4種、カスタム単体テスト

**実施メモ**: dbt 1.11推奨の `data_tests:` 構文（旧`tests:`のエイリアス）で統一。カスタムSQLテスト（singular test）は5件作成（`quantity`/`sales_price`/`current_price`のマイナスチェック、`order_count`の下限チェック、`total_net_paid`のマイナスチェック）。詳細は[`docs/step3_step4_学習まとめ.md`](step3_step4_学習まとめ.md)参照。

## ステップ5: incrementalモデルを試す ✅完了

**目的**: 大量データの差分更新パターンを覚える

**やること**:
- `store_sales` を使ったincrementalモデルを作成
- `is_incremental()` フィルタで差分取得を実装

```sql
{{ config(materialized='incremental', unique_key='ss_ticket_number') }}
select ...
{% if is_incremental() %}
  where ss_sold_date_sk > (select max(ss_sold_date_sk) from {{ this }})
{% endif %}
```

**学べること**: incrementalの仕組み、コスト削減の考え方

**実施メモ**: 計画時の想定から実装が発展し、以下の内容になった。

- `stg_store_sales` とは別に検証専用モデル `stg_store_sales_incremental` を新設
- コスト抑制のため店舗を1店（`ss_store_sk = 502`）に絞り込み
- `unique_key` はデータ粒度（1チケット内の1商品明細）に合わせ `['ticket_number', 'item_sk']` の複合キーを採用
- 取り込み範囲の上限を `var('max_date_sk')` で可変にし、`--vars` を変えながら3段階（01/03→01/05）で差分マージの挙動を検証
- 複合キーの一意性テストのため `dbt-labs/dbt_utils` パッケージを導入（`dbt_utils.unique_combination_of_columns`）

詳細は[`docs/step5_step6_学習まとめ.md`](step5_step6_学習まとめ.md)参照。

## コスト注意事項

- ウェアハウスは常に **X-Small** を使用
- `dbt run` 後は Snowflake コンソールでウェアハウスが停止していることを確認
- `dbt compile` で SQL を確認してから `dbt run` する習慣をつける
- Dynamic Table等、`dbt run`と無関係に裏でリフレッシュが走る機能を使う場合は、検証後に`SUSPEND`／削除を忘れない
