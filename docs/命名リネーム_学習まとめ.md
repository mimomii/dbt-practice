# 命名リネーム 学習まとめ

使用データ: `SNOWFLAKE_SAMPLE_DATA.TPCDS_SF10TCL`（小売業の取引データ）

ステップ番号を持たない独立作業として、モデル・YAMLファイルの命名をdbt Labs公式ガイド「[How we structure our dbt projects](https://docs.getdbt.com/best-practices)」に準拠させた（ステップ7完了後、ステップ8着手前に実施）。今後モデル・YAMLファイルが増える前に命名規則を確定させておく目的。

---

## 目的

- dbt公式のベストプラクティスガイドが推奨する命名慣習を確認し、プロジェクトに適用する
- 今後モデルが増えていく前に、一貫した命名ルールを確定させる

## 決定事項

### モデルファイル

| 現在 | 新 | 理由 |
|---|---|---|
| `stg_customer` | `stg_customers` | staging層はエンティティ名を複数形にする公式慣習 |
| `stg_item` | `stg_items` | 同上 |
| `stg_date_dim` / `stg_store_sales` | 変更なし | 元から複数形／固有のディメンション名 |
| `stg_store_sales_incremental` | 変更なし（対象外） | 物理テーブル（incremental）のため、リネームすると次回実行時に新テーブルとして再構築され、ステップ5・8で積み上げた差分マージ履歴が失われる。命名の一貫性よりデータ保護を優先 |
| `int_sales_with_customer` | `int_store_sales_enriched` | intermediate層は「int_[エンティティ]_[動詞]」形式が公式慣習 |
| `int_daily_sales` | `int_store_sales_aggregated_to_day` | 同上（集計先の粒度を動詞句で表現） |
| `mart_monthly_sales` | `fct_monthly_sales` | marts層はファクト（`fct_`）／ディメンション（`dim_`）を使い分ける公式慣習。集計されたイベントデータのためファクト |
| `mart_customer_summary` | `fct_customer_summary` | 顧客の属性テーブルではなく集計指標が中心のため`dim_`ではなく`fct_`を採用 |

### YAML/Markdownファイル

| 現在 | 新 |
|---|---|
| `models/staging/sources.yml` | `models/staging/_staging__sources.yml` |
| `models/staging/schema.yml` | `models/staging/_staging__models.yml` |
| `models/intermediate/schema.yml` | `models/intermediate/_intermediate__models.yml` |
| `models/marts/schema.yml` | `models/marts/_marts__models.yml` |
| `models/docs.md` | `models/staging/_staging__docs.md`（内容がstaging専用のため配置も移動） |
| `macros/schema.yml` | `macros/_macros__macros.yml`（公式ガイドがmacros側の命名を明示していないため、models側の慣習を拡張して適用） |

アンダースコア接頭辞は、ディレクトリ内で`.sql`ファイルより上に表示させるための公式ガイドの慣習。

## 進め方

1. `git mv`でファイルをリネーム（履歴を保持）
2. `ref()`呼び出し元・`schema.yml`の`name:`・`relationships`テストの`to: ref(...)`・カスタムSQLテストを`sed`で一括修正
3. `dbt parse`で構文チェック（Snowflakeに接続せず高速に確認）
4. `dbt docs generate`でschema.ymlの整合性を確認
5. `dbt run --select <新モデル名...>`で新しい名前のオブジェクトを作成
6. `dbt test --select <新モデル名...>`で全件PASSを確認
7. Snowflake上に残る旧名オブジェクト（view）をSnowsightから手動`drop view`
8. YAML/Markdownファイルをリネーム（内容は無変更、ファイル名・配置のみ変更）
9. 再度`dbt parse` / `dbt docs generate` / `dbt test`で最終確認

## Tips: 詰まったポイント

### 1. `sed`のインデント想定ミスで一部の`name:`置換が漏れた

**詰まった内容**: `schema.yml`内のモデル定義（`- name: stg_customer`）を`sed`で置換する際、staging用のパターンだけインデントを4スペースと誤って想定してしまい（実際は2スペース）、`stg_customer`/`stg_item`の`name:`フィールドが置き換わらないまま残った。`ref()`側は正しく置換されていたため、`dbt parse`は一見通ってしまう状態だった。

**発見の経緯**: 全ファイルを対象に古いモデル名の残存を`grep`で横断チェックしたところ、`schema.yml`側の`name:`定義だけが取り残されているのが見つかった。

**教訓**: 複数ファイルに同種の`sed`置換をかけるとき、ファイルごとにインデントの前提が異なる場合がある。置換後は「置換されたはず」で終わらせず、古い文字列がプロジェクト全体にまだ残っていないか横断`grep`で確認する習慣が重要。

### 2. `ref()`ではない説明文（description）中の古いモデル名は`dbt parse`では検知できない

**詰まった内容**: `schema.yml`の`description`に平文で書かれた古いモデル名（例:「`int_sales_with_customer`をcustomer_idでグループ化し...」）は、Jinjaの`ref()`のように依存関係として解決されるものではないため、リネームを忘れても`dbt parse`・`dbt compile`はエラーにならず素通りしてしまう。

**教訓**: モデル名の変更は「構文的な参照（`ref()`, `to: ref(...)`）」と「説明文の中のプレーンテキスト」の2種類に影響する。前者はコマンドが検知してくれるが、後者はコマンドでは検知できないため、`grep`による横断チェックを別途行う必要がある。

### 3. モデルをリネームしてもSnowflake上の旧オブジェクトは自動削除されない

**詰まった内容**: `view`マテリアライズのモデルをリネームして`dbt run`すると、新しい名前のviewは作られるが、古い名前のviewはSnowflake上にそのまま残る（dbtは現在定義されているモデルに基づいてCREATE OR REPLACEするだけで、過去に存在した名前のオブジェクトを把握・削除する仕組みを持たない）。

**対応**: Snowsightのワークシートで`drop view if exists`を手動実行して後始末した。

**教訓**: incrementalモデル（物理テーブル）だけでなく、view単位でも「リネーム＝旧オブジェクトの孤児化」が起きる。renameを伴うリファクタリングでは、コード側の変更が完了した後にウェアハウス側のクリーンアップ手順も忘れずに計画に含める必要がある。
